# 行为验证记录

验证日期：2026-10-29。基于独立 agent 的实际产物与主 agent 核对，全部使用隔离项目，无网络、提交或真实用户配置修改。

## 基线与 Skill 对照

五个样本的原始材料相同；无 Skill 和有 Skill 的执行者分开，均未读取预期验收答案。主 agent 先观察基线，再编写规范。样本是教学用小项目，不能代表所有真实仓库。

| 场景 | 无 Skill 实际观察 | 有 Skill 实际观察 |
|---|---|---|
| 已有执行器 | 保留 jmvn/Git/语言约束；状态、异常、旧字段准确；当前与未来分开；没有独立文档标准 | 保留约束与当前契约文件，增加文档标准和开发入口；不复制一套架构文档 |
| 空项目 | 两份入口，无虚构实现 | 三份必要入口含文档标准，无虚构命令、架构或教训 |
| 原有 ADR | 保留路径与编号，补导航 | 保留原文与 accepted 状态，显式映射决策角色；没有源码就不称实现已验证 |
| 提案完成 | 正确移到 implemented；自定头部和章节，夹带迁移经过和验收历史 | 使用规范头部和当前决定/替代方案/后果，明确清理能力完成但切换调用方不存在 |
| 教训晋升 | 正确提炼长期要求，但完整配置防错细则进入根 AGENTS | 完整规则进入领域防错页，根指令导航，LESSONS 留摘要、证据和去向 |

基线已有较强的事实判断，因此没有把所有场景都记为失败。Skill 的可观察改进集中于文档标准持久化、规范格式、领域规则归属和证据边界。

## 有 Skill 的实测结果

第二轮复读后没有新增重复所有者；删除一处 Note 重复接口细节，改为链接 README，并移除空 proposed 目录。这是一次人工驱动的重复维护观察，不等同于任意生成过程字节级幂等。

## 验证中修正的问题

- 局部维护与默认必要入口之间存在张力：补充显式配置范围和不得冒称全仓采用的说明。
- 空项目文档规范容易过长：补充三段最小标准，随着真实内容增长再展开。
- 独立评审发现预算覆盖漏检：规范路径、父级排除、非 Markdown 预算和归档提前返回；新增真实临时目录回归并修复。
- 主实现发现决策树导航误判和显式文件被目录链接跳过：分别增加回归，避免误报及覆盖范围假成功。

机械测试使用标准库 unittest 和真实 CLI subprocess，当前 37 项全部通过。系统 Skill 元数据校验通过；正文资源检查无错误（模板有意保留占位符，通过 tests/skill-doc-rules.json 明确排除，模板正文由内容审查覆盖）。结果以实际运行输出为准，不通过测试数量推断文档语义正确。

## 目录内部组织增量验证

同日使用相同原始文档样本，由独立 agent 分别使用旧版副本和新增目录契约的版本整理。评估者不读取验收答案，样本只有已确认文档，没有源码。请求仅允许整理 docs，已有 user/index 是网站稳定入口，ADR 编号受外部引用，图片位于根 images。

旧版已能拆开任务/配置契约、具体化教程命名、保留兼容链接和原资源；未把这些已有能力记作失败。观察到的缺口是把用户入口扩成 ADR、事故、内部参考与操作的全仓导航，没有明确区分用户和维护者读者。

新版在 docs/AGENTS 持久化文件单位、主题/动作命名、浅层分组、入口排序、资源和稳定路径例外；保留现有 Cookbook 管理员操作映射，user/index 只导航用户任务，docs/README 承担维护者跨类别导航，system 复用为子系统选择入口。根 README 仍引用的旧路径保留兼容导航，正文没有双份维护。ADR 路径、编号、正文及 accepted 状态不变；范围外图片保持原路径，明确唯一消费者。

两轮机械检查均覆盖 12 个 Markdown，0 错误、1 条 external ADR 人工核验提示，无额外排除。独立内存检查核对根约束、README、ADR、图片保留 4/4，从根 README 可达 docs 页面 10/10，三个主题正文唯一所有者 3/3。第二轮未再次改名、拆页或新增重复所有者。该可达性/所有权核对是本样本的额外人工与内存检查，不属于通用检查器能力。

未验证实际运行、安装操作、事故修复、网站路由和图片视觉呈现。独立评审发现职责表、模板与示例的旧 Cookbook 表述和新增默认读者边界冲突，已同步明确产品用户任务默认进 user、贡献者操作默认进 Cookbook，既有映射可保留。

## 决策协作与Cookbook增量验证

独立执行者只使用project-docs，按真实generator.py编写贡献者生成报告教程，实际运行生成、JSON内容检查、缺参失败、路径失败、恢复和清理；没有修改业务源码或原ADR。局部SQLite提交/回滚/错误传播测试通过，但消费者迁移证据不足，提案仍proposed。既有ADR以external保留编号、状态和正文。

该项目随后由另一执行者只使用decision-records读取同一项目规则并治理。共同状态/部分取代判断一致，未重新定义规则。专项操作按新授权首次封存旧缓存，报告当前一致性与无可信历史保护的区别。

实际发现并修正：单次「本次不归档」被误写入长期约定，补充持久化与交付范围分离，要求清除残留并复核。执行者初称三个原链接被漏检，经主实现对原始材料和命令核对确认链接本来正确、检查器符合预期；该漏检说法不计入缺陷或验证成果。

## 开发规范增量验证

2026-10-30，更新前后由不同独立执行者使用各自版本的 project-docs，分别整理相同原始资料的新项目和既有 conventions 项目。执行者不读取验收答案和其他评估结果，仅允许编辑隔离样本的文档。新项目有真实本地 JSON 工具和已采纳命名/编码要求，既有项目有 app → infrastructure 写盘路径、稳定规范入口和未实现的配置更新规则。

旧版已能保留强制/建议、外部字段/编码例外、已有路径和唯一正文，也能写出评审导航；不把这些能力记作新增收益。缺口是新项目自行选择 conventions 和独立 defensive-patterns，尚无已确认的 standards 默认布局和专门规范内容契约。

新版新项目将真实规范放入 standards/coding 和 standards/defensive-patterns/file-encoding，入口按任务导航，原 POLICY 改为兼容导航。既有项目保留 conventions/index 和独立 defensive-patterns，明确角色映射，没有竞争的 standards 树。两者根指令导航开发与评审，docs/AGENTS 仅管文档；命令、测试说明与规范正文分别归属，不制造事故、审批、架构或决策空壳。

两轮检查中新项目 9 篇、既有项目 8 篇 Markdown 均零错误、零警告。主执行者复跑同一检查结果一致，从 README/根 AGENTS 遍历链接分别可达 9/9 和 8/8，原有 Python 源文件逐字节保持不变。执行者报告第二轮文档哈希不变，并实际运行中文数组计数、中文报告导出和命名检查；新项目还检查坏 JSON 在输出写入前失败且原输出字节保留。生成的 Python 缓存已清理，未写用户真实配置。

独立内容复核发现旧防错模板强求「真实缺陷」与已确认要求可直接作为规范来源不一致，已改为要求/团队约定/真实缺陷的适用依据，不编造事故。未验证不存在的配置更新实现、非 UTF-8 例外和完整故障矩阵；链接可达性是样本额外核对，不是通用检查器新增能力。此次未改检查器源码，不把目录/模板调整声称为新的自动语义检查。
