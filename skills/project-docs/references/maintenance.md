# 维护与审查

## 按变化选择更新

| 变化 | 需要核对的所有者 |
|---|---|
| 接口、职责、状态、失败、兼容保证变化 | 子系统参考与模块 README；架构关系变了再更新 architecture |
| 配置、默认值、安装、操作变化 | 模块 README、development 或对应 Cookbook |
| 环境、测试隔离、验证入口变化 | development / testing；命令仍以构建配置为准 |
| 影响后续维护的长期设计取舍 | 已有 Agent Note，或满足创建条件时新增 |
| 已批准提案实施完成 | 状态、路径、正文和引用一起更新 |
| 决定部分/完全取代、合并清理或冻结归档 | 先读项目决策约定；基本操作遵守本 Skill 决策规范，专项治理可用 decision-records；记录两类验证的实际范围 |
| 开发操作教程变化 | 按 Cookbook 编写流程核对实际步骤、结果、副作用和恢复，不复制另一个同义教程 |
| 返工、漏检、事故 | 有证据的 LESSONS；需要因果复盘时另写 postmortem |
| 纯内部整理、机械改名、局部展示 | 只更新受影响的事实和路径，不强制新增 Note 或经验 |
| 页面新增、删除、拆分、合并或目录调整 | 按目录契约核对文件单位、命名、最近有效导航、入站引用、资源与公开入口；不机械生成所有层级索引 |

先读取所属文档和实际运行路径，再对照 diff、调用方、状态和测试核对变化。一个函数正确不等于整个操作满足保证；执行路径通过插件、配置或进程间调用时，确认实际所有者。

## 审查输出

默认只读。每项问题包含文件和位置、违反的内容契约、现有证据、会影响谁、建议归属与修复。明确区分：

- 可复核的错误：坏链接、状态不一致、命令执行失败、源码与说明矛盾。
- 内容缺口：关键失败或生命周期未交代，需核对实现才能补全。
- 改进建议：职责划分或写法可以更清楚，但不伪称为已证实缺陷。

没有发现问题时仍报告读过的范围和未验证部分，不凭格式通过宣称内容正确。

## 逐文档核验

1. 读者能回答什么问题？是否放在最低合适所有者？
2. 内容契约中哪些项适用，是否覆盖条件、失败和边界？
3. 每个重要字段、默认值、状态和命令来自哪里？
4. 是否重复其他文档、源码清单或生成内容？
5. 是否夹带未实施计划、推理过程、任务流水账或无依据的替代方案？
6. 改动是否修复所有受影响引用，当前与历史是否分清？
7. 若改变目录或新增页面，是否按 [目录契约](directory-layout.md) 明确文件单位、命名与分组？页面能否从当前阅读入口到达？资源是否有所有者？已有网站入口和决策编号是否保留？

## 验证和报告

先运行 [机械检查](checker.md)，再进行上述语义核验。单条决策等局部维护不为了默认必要入口额外初始化整套文档：通过显式配置声明本次真实需要的入口，报告实际覆盖范围；这不表示全仓文档规范已采用。新增命令或操作说明尽可能按文档原样执行，并核对输出、副作用和失败行为；需要外部服务、凭据、付费或不在当前授权范围的操作，报告条件与未执行原因。不要展示秘密或触碰用户真实配置来完成测试。

代码未变化时无需为文档任务运行整个应用测试套件；实际操作示例和目标项目要求的文档检查仍需验证。对检查器代码变更运行其用例，对模板变更使用真实最小项目核对生成内容。

交付报告简述文件归属、保留约定、实际验证结果、跳过/未验证项、后续责任。目录任务同时报告分类和命名选择、入口与例外、拆分依据及资源迁移。脚本不覆盖目录语义、导航完整性、外链、锚点和内容语义；需要时使用项目已有工具或人工检查，不自行把「未检查」转成「通过」。
