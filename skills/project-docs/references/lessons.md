# 有证据的开发教训

## 何时记录

记录实际返工、重复缺陷、漏检或事故中能改变未来行动的经验。普通修改、一次顺利完成的任务、个人偏好不自动成为教训。不扫描历史后臆测原因，不把别的仓库的事故算作本项目发生记录。

## 每条内容

- 简短稳定的主题与适用场景。
- 一条可执行规则，说明应采取什么行动以及避免哪种失败。
- 真实事实：哪里出了问题，已有检查为何没捕获。
- 可核对的提交、问题、测试或事故文档链接；缺少实现核验时明确限制。
- 独立发生日期/次数；同一事件的多次讨论不能重复计数。
- 状态：候选、已晋升或已失效，以及正式规则或替代结论去向。

## 晋升

同类问题在三个不同日期发生，默认建议晋升为正式项目规范；一次高影响事故也可直接晋升，给出证据和理由。次数是判断信号，不是自动审批或强制复制规则。

领域内要求进入模块参考或 `docs/defensive-patterns/<domain>.md`；文档写法进入 docs/AGENTS；全仓始终需要的简短约束才放根 AGENTS。例如「读取失败不能覆盖配置」的完整规则、失败案例、例外和验证应放配置领域防错页，根指令只写「修改配置处理前读该页」。

晋升时完整规则只保留一个所有者，LESSONS 留主题、事件证据、状态和正式链接。不要同时维护根 AGENTS、LESSONS、代码标准三份相同正文。由经验推导的新规则要核对项目现有约定，不能扩大既有用户限制或创造无依据审批。

## 退役与控制篇幅

规则不再适用时核对原因，修正或移出活动教训；有事故价值的细节移到 postmortem，不无限增长根文件。LESSONS 的入口和候选摘要保持可扫描，按相关领域读取细节。

未发生事件的项目可以只保留这套简短记录约定。禁止捏造首条经验，不自动安排定时复盘，也不把日报写进 LESSONS。
