# 目录内部组织契约

## 使用与优先级

在初始化、迁移、目录审查、新增页面或改变分组时读取。本文件拥有目录内的组织规则，[事实归属](document-ownership.md) 决定文档角色，[内容契约](content-contracts.md) 决定每篇需要讲清楚什么。

以下是没有既有约定时的默认方案。先保留用户约束、现有 ADR 编号、网站入口和公开链接，再明确本项目采用的路径、文件单位、命名和导航方式。改变旧路径必须有具体收益及引用迁移方案，不能仅为了统一外观重命名。没有内容就不创建目录或入口。

## 每类目录的内部规则

| 目录角色 | 文件单位与默认布局 | 命名与导航 |
|---|---|---|
| `docs/` | 根层保留全局说明、架构、开发、测试和分类入口；独立领域或任务群进入所属目录，不无限堆积无关页面 | 参考用具体主题名；总入口复用既有 README、index 或网站导航，小项目可由项目 README 直接导航 |
| `subsystems/` | 同级子系统默认平铺，一页拥有一个跨模块契约；不按源码文件或每个 API 拆页 | `<subsystem>.md`；出现多篇并列参考时提供导航，说明每页拥有的语义。不要把逻辑平级的子系统任意嵌套 |
| `cookbook/` | 默认面向贡献者，一篇完成一个实现、集成或维护目标，先平铺；独立任务群确需独立导航、读者或维护时才分子目录；已有产品教程按明确映射保留 | 动作与对象，如 `add-provider.md`、`configure-build-proxy.md`；入口按任务/前提导航，避免 `guide.md`、`misc.md` 之类无法判断目的的名称 |
| `standards/` | 正式开发规范的默认位置，一篇拥有一个可独立维护的主题，先平铺；如编码、依赖边界、评审要求，不按每条规则拆页 | 如 `coding.md`、`dependencies.md`、`code-review.md`；有多篇规范时复用/建立 README，说明强制与建议的区别，并按开发/评审任务导航 |
| `standards/defensive-patterns/` | 正式规范中的领域防错类别；按领域或修改对象组织，一篇可容纳理解同一义务必需的紧密规则；存在独立所有者或验证时再拆 | 如 `configuration.md`、`subprocess-lifecycle.md`；入口用「修改什么 → 读哪页」导航，不把所有规则持续堆进 general；少量页面可由 standards 入口直接导航 |
| `postmortem/` | 一篇记录一次事故；重复问题仍保留独立事件证据，长期共性进入正式规则 | 新项目默认 `YYYY-MM-DD-<incident>.md`；已有 `0007-<incident>.md` 等稳定编号保留并声明。多事件入口列主题、日期/编号和链接，不复制时间线 |
| `user/` | 按真实用户任务组织，起步页指向最短成功路径；独立任务群出现时再分组，开发贡献流程留在开发文档 | 如 `quickstart.md`、`configure-account.md`；有足够内容时可用 `guide/`、`advanced/` 等明确分组，不预建空壳；复用既有 index/README |
| 决策目录 | 状态/类别组织默认布局或保留现有 ADR；不能为每个状态和类别强制生成入口 | 见 [决策规范](decision-records.md)。约定入口解释格式、状态和搜索方式，不维护第二份集中状态清单 |
| 资源与样例 | 所有者明确的图片、数据和可运行样例靠近所属主题；真实测试夹具留在测试代码所有者附近 | 多页共享资源可用 `assets/<topic>/`，单一主题也可使用 `<topic>/assets/`；链接相对文档定位，避免无归属的 images 或附件堆积 |
| 生成参考与网站 | 沿用实际生成器的路径与发布映射，手写内容和生成产物范围明确 | 不手改派生文件。迁移必须同时检查源文件链接、公开路由、别名和生成配置 |

源码模块自己的 README 留在模块旁，不为了将所有文件放进 docs 而迁移。升级说明、协议历史等专门角色只有项目确需维护时才增加，先定义文件单位、命名、权威入口和验证方法，不能形成含糊的「其他文档」目录。

已有 `docs/conventions/`、`guidelines/`、`docs/defensive-patterns/` 或其他有效规范路径时，保留并声明对应角色，不因新默认布局迁移或创建竞争的 standards 树。`development.md` 拥有环境与日常操作，`testing.md` 拥有测试选择、隔离与结果判断；规范引用这些唯一所有者，不另复制一套步骤/规则。架构参考描述现行依赖关系，standards 只有确需独立表达的开发要求，二者不重复维护同一保证。仅有一个主题时可用单页并由父级导航，未采纳规则或没有实际内容时不建目录。

同时采用 user 与 cookbook 时先区分读者：新项目默认把产品使用者/管理员操作放 user，把贡献者的实现、集成和维护操作放 cookbook。已有项目若将产品操作教程统一放 cookbook，可保留并明确角色映射，由 user 导航到唯一正文；不能在两个目录各维护相同步骤。保留稳定 user/index 不代表它应收纳 ADR、事故和内部契约的全仓索引，跨读者内容由相应开发入口发现。

## 命名与层级

新文件默认小写英文单词以连字符连接，中文正文不要求中文路径；保留 README.md、AGENTS.md 和工具约定的特殊文件名。名称表达文档任务或主题，不用 `new`、`final`、`v2`、作者名或随机编号表达当前正文状态。日期/版本用于真实的事件、决策或版本历史，不给当前参考随意加日期。

同一目录优先使用一种分类维度。教程按用户目标分，子系统参考按契约所有者分；不要同时混用状态、技术栈、作者和业务领域，造成同一页面多个可放位置。分组名称必须能说明孩子共同的职责，不能仅靠缩短目录列表证明需要分组。

默认浅层，按真实所有权和检索需要增加层级。页数或字数只提示检查，不自动触发嵌套。一个主题只有一页时，优先文件；若同时拥有独立子主题或资源，再考虑主题目录。不机械要求每个叶目录都有 README。

## 入口与可发现性

根 AGENTS 是行动入口，目录入口是阅读导航，两者职责不同。每个当前维护页应能从项目已有阅读入口沿有效链接找到，或通过项目明确采用的生成导航/检索清单发现；不能仅因文件存在就视为可发现。决策目录通过格式说明和路径搜索发现是合法例外。

有多篇并列主题且读者需要选择时，创建或复用目录入口。默认 README.md；已有网站使用 index.md 或导航配置时复用该入口，避免 README 与 index 竞争同一导航职责。父级能清楚覆盖小目录的直接页面时可以不增加子级入口，但在目录增长后重新评估。

入口用短段落说明范围和读者，按职责或任务链接直接子页面/子目录，并说明每项解决的问题或拥有的内容。顺序根据先决条件、用户任务或稳定主题排列，并在项目约定中明确。不能复制子页面规则、全量 API 或整棵树，更不能同时维护多份状态清单。格式见 [目录入口内容契约](content-contracts.md#目录入口页)。

新增、移除、拆分、合并或更名页面时，在同一变更更新最近的有效导航和全部受影响引用。公开入口受兼容约束时保留路由/别名或提供明确迁移，不能只修仓库 Markdown 后就声称外部链接正常。

## 拆分、合并和资源迁移

有独立读者、契约所有者、更新节奏、稳定入站链接或验证对象时考虑拆分；同一个问题需要连续跨多页才能理解时保持一起。混合两个不相关子系统的参考可拆成两份具体主题，原页仅在仍有真实概览/兼容导航价值时保留，不能继续拥有两份契约正文。

拆分先确定每项事实的新所有者，再在当前授权范围内移动正文和资源、修复图片/样例引用、更新导航和适用检查。合并前保留独特例外、限制、理由与证据。资源需要一起移动时先搜索其他消费者；资源位于本次范围外时保留路径，记录所有者与位置例外，不通过复制文件规避范围约束。共享资源保留一个所有者，不复制多份来避开修链接。相对路径示例要依据新文件位置重算。

临时草稿不混进当前参考。只有确需共享交接且已有到期/晋升约定时才跟踪临时文档；不要为每次会话创建 scratch。完成后把稳定事实和理由分别移入所属文档，清除已解决的临时内容。

## 写回项目与验收

在 `docs/AGENTS.md` 或其项目内唯一规则所有者中，记录实际采用的目录角色、文件单位、命名、入口与排序、资源位置及稳定路径例外。小项目用短段落，复杂项目用表格；无需把本文件全文复制过去。必须足够具体，使未安装 Skill 的后续 agent 能正确放置新页面。

人工核对：新页应放哪里、叫什么、是否拆分、入口如何到达、资源属于谁、迁移要改哪些引用，均能从项目约定得到答案。机械检查仅证明已覆盖的目标存在等条件，不自动判断目录分类、可发现性、索引完整性或拆分是否合理；如项目已有显式导航清单或命名检查，使用其真实命令。没有此类检查时报告人工核对范围，不能宣称已自动验证。
