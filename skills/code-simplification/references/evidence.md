# 证据与候选判定

## 范围和权威

先确认用户是在调查、评估一个方案还是要求实现。确定项目根、实际分支/版本、调查目录和部署/构建入口。读实际生效的指令、架构、测试与相关活动决定，记录明确保留能力、兼容承诺和目前看不到的消费者。

已有理由可以说明意图，但仍应对照当前实现；一个提案自身新增的要求或测试不是其必要性的独立证据。历史拒绝要读具体失败前提，不当永久技术黑名单。归档记录只解释历史，不能据此修复其出站引用或当作当前权威。

## 完整效果路径

先用rg等现有工具搜索，再读匹配和上下文。除符号名外，查属性读写、字符串标签、配置键、构造与emit端、注册表、导出与入口、方法的不同调用形式。为每个候选找到生产者、转换/存储、实际加载或分发、消费者和最终效果。

根据项目实际查配置/清单加载、插件注册、反射、依赖注入、生成产物、脚本入口、安装包、公共SDK/CLI和跨进程协议。样例/测试所在目录名不能决定它是不是产品路径。生成目录依赖其权威输入和真正消费者，不能只搜手写源码。源码运行与构建产物运行都存在时核对两者。

测试、类型声明和序列化分支可能只证明接口存在；也可能承载真实支持能力。仓内没有调用不证明第三方接口无用；不能访问外部消费者时说明限制和兼容义务，不因缺少搜索结果就删除。

## 候选证据单

每项候选至少回答：

| 字段 | 必要内容 |
|---|---|
| 当前所有者 | 实现、数据和使用方在哪里，为什么由此处承担 |
| 实际路径 | 生产与消费证据、动态入口、配置优先级、效果或无效点 |
| 减少责任 | 删除的实现/状态/API/配置/测试/文档与整条生命周期 |
| 剩余与新增 | 适配、依赖、配置、平台、验证和迁移成本，避免只算删除 |
| 行为影响 | 哪些输入、消费者、兼容、持久化、失败或性能保证会变化 |
| 保留理由 | 支持原设计的最强真实证据与否决条件 |
| 验收证据 | 能推翻方案的检查、已运行结果、缺口与范围 |

量化来自实际测量或可核对差异，没有可靠数字就用具体责任描述。行数、文件数或包数量只是辅助信息，不能代替维护收益。

## 分类与结论

- **可实施的保义务简化：** 证据覆盖保留的契约，确有净维护减少；不承诺无法核对的外部等价。
- **需要行为取舍：** 当前有用能力也可能过于昂贵，但必须明说放弃什么、影响谁、迁移和回退代价；用户只要求调查时仅提建议。
- **保留或暂缓：** 破坏明确保留的义务、只是挪动复杂性、净收益不足或证据不够。说明拒绝依据，避免下次无新证据重复提出。

公开字段即使所有实现都忽略，删除仍可能改变输入接受、校验、序列化或第三方编译契约，不能直接归类为纯死代码。私有不可达元素也需检查项目实际允许的动态访问；报告证据边界。
