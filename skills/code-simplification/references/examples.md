# 正反案例

以下为独立教学案例，不能当作目标项目的真实缺陷。先核对当前生产消费、项目约定和证据范围，再使用模式。

## 无直接import的插件

runner读取配置中的`plugins.json_renderer`，通过动态模块加载后调用render，最终生成用户输出。静态搜索只找到配置字符串、实现和测试。

结论：插件有完整实际效果路径，不能凭无固定import删除。硬编码序列化虽然代码更短，却丢失可配置插件能力；若用户愿意放弃该能力，另行明确取舍和迁移。验证应走真实配置加载，不只直接调用json_renderer。

## 私有旧清单

同一runner中有私有`_legacy_names()`返回旧名称列表；代码、实际配置、注册入口与构建路径均不读取它，项目没有承诺通过动态反射访问该私有名称。

结论：可以建议删除，减少一份无效手工清单。收益只是小规模维护减少，不足以支持重写整个插件架构。说明搜索边界，实施授权仅覆盖该项时保留其他接口与测试，不强制写新设计记录。

## 公开注册接口

register_loader在仓内无固定业务调用，但公开文档承诺第三方注册，load按名称消费注册，disposer负责释放。现有测试覆盖注册与清理。

结论：保留公开能力；仓内调用为零不是不可达证明。删注册和其测试只是取消能力与验证，不是等价简化。若修改对外承诺，需要明确的兼容策略和相应授权。

## 界面忽略的开始事件

display只显示done事件，recover用running与done恢复尚未完成的任务。去掉running会让空输出任务、失败任务或崩溃中断不可恢复。

结论：可以评估显示层投影，不能据此删除持久事实。验收应包括先开始未结束的任务；只看最终成功界面会漏掉被破坏的恢复能力。

## 缓存和依赖替换

消费者本就需要读取权威快照时，重复缓存与失效订阅可能可以一起删除；但离线使用或需要采集时刻值的消费者使其仍有责任。先明确时机，不把所有缓存都当冗余。

一个库可以替代自建流解析，但若为保留大小上限、截断与取消又写回同样缓冲层，净维护成本未必降低。只有核对被删除机制、剩余适配与行为代价后，才形成候选。库更短或测试更少不足以证明简化。

## 方案自身的理由

一个PR增加三种状态并写测试保证三种状态都存在。测试证明实现符合该PR的设计，不能独自证明消费者需要这三种状态。反过来，已有决定说明某状态用于协议兼容时，应核对当前消费者与旧数据，不能因状态看起来复杂就删。
