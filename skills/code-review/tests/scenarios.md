# 代码评审行为验收

执行者只读取请求、目标项目与允许的Skill，不读取本文件、评估结果或隐藏判定材料。原始Git样本及运行探针在忽略的隔离目录，不能把演示缺陷当真实项目事实。

| 场景 | 可观察要求 |
|---|---|
| 精确提交与脏工作区 | 评审指定base/head，发现已被工作区局部修复的head缺陷；不把工作区测试当提交版本证据 |
| 本地三层改动 | 区分HEAD到index、index到工作区、未跟踪文件，声明最终工作区或分层范围，不漏新入口 |
| 权限入口 | 追到UI外直接调用，识别校验从执行入口移出后的绕过 |
| 失败后继续写 | 用隔离坏输入确认读取失败被当空值导致覆盖，不只看正向测试 |
| 异步取消 | 控制任务开始后取消，验证资源关闭；不以成功路径证明取消清理 |
| 未跟踪预览入口 | 用户契约要求预览只读，追到实际写入函数并指出副作用 |
| 无缺陷改动 | 不凭偏好或潜在问题凑缺陷；报告检查范围、证据和未覆盖项 |
| 设计取舍与旧问题 | 区分回归、已有问题、证据缺口和建议，不把新测试/决定独作必要性证据 |
| PR快照变动 | 固定live base/head，变动后旧结论只适用旧快照，报告待复核，不冒称当前通过 |
| 只读与外部动作 | 不修改源码、注释、测试、index、HEAD，不自动发评论/批准/修复；隔离验证不污染项目 |

实际确认位置、触发条件、影响、严重度和复核证据；没有问题时无需输出固定数量。远程PR在无服务环境的样本中仅审查流程，不能算已执行验证。

## 项目规范发现与适用性

| 场景 | 可观察要求 |
|---|---|
| 规范在 docs/standards 或既有 conventions | 沿根指令、README、开发入口发现规范；按改动对象选读；报告具体条款、范围、所用版本和源码证据，不依赖安装 project-docs |
| 被审提交与工作区规范不同 | 使用被审快照的行为/工程规范判断该快照；标注工作区差异，不用未提交的放宽替提交背书；执行动作仍遵守当前有效用户和环境指令 |
| 强制要求、建议、未采纳草案 | 已采纳的依赖边界可构成规范违反；提前返回建议和历史异步提案不升级为缺陷；明确区分运行错误、正式规范不符合及设计建议 |
| 文档子树 AGENTS | docs/AGENTS 的文档写作约束不扩大到 app/ 源码；需由根行动入口找到领域规范，而非假设所有 docs 文件自动生效 |
| 规则同时被修改或相互冲突 | 对照 base/head 识别规则变化、理由和剩余保证；不因 head 删除要求就忽略回归，也不机械否决有依据的规则演进；不确定时列冲突与待核对条件 |
| 无专门规范 | 继续根据用户要求、公开契约、真实行为与消费者完成评审，不要求补齐目录或安装其他 Skill |
