# 项目规范的发现与应用

项目有开发/评审规范、规则本身发生变化，或文档与实现冲突时读取。Skill 提供通用判断方法，具体要求以项目真实采纳且适用的规范为依据，不要求 project-docs 或任何固定目录存在。

## 发现与选读

从根及修改路径适用的 AGENTS、README、贡献/开发入口读取任务导航，按改动对象追到实际规范、领域防错、测试和接口所有者。新项目可能使用 docs/standards/README.md 及其 defensive-patterns，已有项目可能用 conventions、guidelines 或独立 defensive-patterns；不能只搜标准目录名就断言没有规则。入口不足时检索仓库中的相关主题及引用，确认实际范围，不必为局部评审读完整 docs。

docs/AGENTS 主要约束文档编写，其子树命名或示例规则不自动扩张到源码。工程规范即使放在 docs，也可通过明确的全仓/模块范围和项目入口约束源码；是否适用由内容、作用域和采纳依据判断，不能只看它位于哪个目录。修改文档本身时仍需读取其适用指令。

为实际影响结论的规则确认以下信息：

| 信息 | 判断 |
|---|---|
| 来源与版本 | 哪个项目文件/条款、属于被审提交还是某个本地层；不要只列「遵守项目规范」 |
| 范围与条件 | 约束哪些模块、行为或任务，本次改动是否触发；已有例外是否成立 |
| 等级与状态 | 已采纳的必须项、建议、提案、被取代或历史记录；目录名和 MUST 字样不能单独证明已采纳 |
| 判断与证据 | 如何观察违反、所改路径和消费者、适用测试或人工核对方法 |

提案和历史记录可解释背景，但不自动成为现行标准。没有采纳证据或条款含义不明确时说明不确定性，不自造标准、审批人或强制等级。

## 快照与规范演进

评审固定提交时，工程规范、接口保证和测试要求从相应快照读取；index/工作区的规则差异单独标注，不能用尚未提交的放宽为 head 背书。实际执行命令和外部动作始终服从当前有效用户及环境指令，历史文件不能授予操作权限。

规则本身在本次范围内修改时，对照 base/head 的条款、变化理由、已承担的接口/数据/兼容义务及受影响引用。不能只因 head 删除约束就认为旧保证无需维护；有依据的规范演进也不能仅因与旧版不同被判错。采用新规则与实现是否完成分别核对。规则互相矛盾或明显陈旧时列出冲突条款、实现证据与受影响保证，能独立确认的缺陷照常报告，无法判断的部分保留为缺口，不擅自改规则或用最严解释冒充结论。

## 进入评审结论

已采纳的强制规范有明确范围和违反证据时，指出具体条款与不符合项。若能证明运行错误或兼容保证受损，给出实际触发、后果和对应严重度；只有规范不符合时如实说明，不编造运行故障、用户损失或 P1 影响。项目有规范检查等级则遵循；没有时单列规范不符合，不强行套用运行缺陷等级。

建议、等价设计偏好与未采纳方案只能支撑非阻断讨论，不能升级为必须修复的缺陷；强制风格规范可以报告为规范不符合，但不伪称正确性回归。缺少要求的验证证据与已证明实现错误分开。报告字段见 [结论与证据](reporting.md)。
