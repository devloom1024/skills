# 独立正反案例

这些是教学案例，不代表目标项目存在相同缺陷。观察真实需求、同版本实现与调用者后再下结论。

## UI校验不能保护直接执行

base在execute内拒绝guest；head把校验挪到click，execute只运行action。界面正向与拒绝测试仍绿，但batch直接调用execute可执行guest动作。

这是明确权限回归，位置应落在移除执行器检查的head差异，证据包括直接调用链与动作副作用。不能把head工作区已加回校验的测试通过当作提交版本无问题；读取固定head并在隔离环境探测。

## 读取失败与写回

read_config以前抛解析异常，现在捕获后返回空对象；update_config随后合并patch并写回。有效JSON测试通过，但坏JSON输入被覆盖为只有新键的文件。

缺陷是旧数据在读取失败后被覆盖，不只是「catch太宽」。用临时文件比较前后字节，并核对base保留文件、head覆盖。若仅缺坏输入测试而实现仍正确，应列证据建议，不能凭测试缺失宣称数据损失。

## 取消与释放

base在finally关闭资源，head将close移到await之后。成功测试仍通过，process异常或开始后取消则跳过close。

用事件确认任务已开始再取消，核对资源是否关闭。不要用固定sleep或成功返回证明取消路径。资源影响依实际类型评严重度，不把任何清理问题一律定P0。

## 本地暂存与最终工作区

index含读取失败回归，未暂存文件修好了它，未跟踪preview又调用了写入函数。若评审最终工作区，可说明index的风险将被工作区修复但单独提交index仍有问题；若只审index，运行最终文件不能证明即将提交内容正确。preview不出现在普通diff，需依据用户范围读取新文件及其只读契约。

## 合理小重构

`return action()`改成`result = action(); return result`，没有改变调用次数、返回值或异常传播。没有对应缺陷时可以无findings；不把「不够简洁」当正确性问题，不因缺专门新测试给出阻断结论。

## 有限证据与设计讨论

没有Windows环境只能说明该平台未验证，不能单凭未知假定失败。一个新状态有真实消费者且项目已说明理由时，不因另一种设计更短就标bug；反之新增测试只断言状态存在，也不能证明它必需。两类意见分别列入验证缺口或设计建议。
