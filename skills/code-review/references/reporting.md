# 结论、严重度与证据校准

## 已证实缺陷

缺陷需要可定位的错误、具体触发条件、实际影响与可复核依据。与所审改动的因果关系清楚；周边未改动代码可提供证据，但定位到引入/激活问题的最小适用diff范围。若必须定位其他位置，解释原因，不能编造改动行号。

每项至少写：简短标题、严重度、文件/版本/位置、触发与调用路径、后果、证据或复现、关键验证限制。相同根因尽量合并，独立影响需独立证据。真实密钥或个人数据用必要脱敏形式表达，不复制到报告。

| 默认级别 | 判断依据 |
|---|---|
| P0 | 普遍且严重的阻断、广泛不可恢复损失或同等紧急影响；不依赖未经证实的特殊前提 |
| P1 | 明确支持路径上的重要能力、安全或数据保证失效，应优先处理；说明实际前提 |
| P2 | 有具体触发和用户/调用方影响的一般正确性问题 |
| P3 | 已证实且影响较小的问题；纯风格和偏好仍不是缺陷 |

目标项目已有等级则使用它，不因框架特定规则把所有类似问题定成P0。概率、影响和适用条件要具体，不能借假设提高严重度。

违反明确契约能证明是缺陷，但不能独自证明影响严重。资源类型、实际泄漏成本或生产作用未知时，不假设连接耗尽、大规模数据损失等后果来升级；说明可观察影响和限制，依据已有证据校准等级。风格建议或未确认风险不进入缺陷等级表。

## 正式规范不符合

项目已采纳的强制规范被本次改动违反时，引用规则路径/条款、版本、适用条件、实际违反位置、证据及已有例外判断。未证明运行影响时单列规范不符合；若同一根因已报告运行缺陷，在其中补规则依据，不重复报两项。只有项目明确规定规范问题的等级时按其等级报告，否则不为条款违反虚构运行严重度。建议、草案与历史约定不能充当强制要求，判断见 [项目规范](project-standards.md)。

## 验证缺口与建议

缺少平台、凭据、上下文、集成测试或实际消费者，只能证明证据不够，不自动证明实现错误。列「已知、未知、为什么重要、下一步怎样区分」。若缺少的是项目明确必需的交付证据，可以指出要求未满足，但不能伪造运行时缺陷或统一给P1。

合理的替代设计、维护偏好、潜在简化与不同架构取舍作为建议，给出依据与代价，不混入已证实缺陷。已有决定可以讨论，不能仅因不喜欢原设计阻断。新测试/新规范/新决定本身也不是必要性的独立证明。

## 无缺陷与旧问题

未发现缺陷时直接说明，并列实际范围、检查和未知项；不输出固定数量，不将「没发现」写成「绝对正确/保证可发布」。旧问题必要时单列与本次关系，避免误归因；本次改动激活旧路径时解释激活条件。

## 位置与发布

本地文件使用真实路径与1起算行号；提交评审说明OID和该快照位置，不能用工作区修复后的行号。PR内联反馈只用已核对当前diff的最小范围；跨文件架构或证据问题放总体说明。没有发评论授权时在当前对话报告，不自动创建远端线程或正式批准。已授权发布也需确认快照没有变动，不能沿用过时位置。

可用 [报告模板](../assets/templates/report.md) 的字段，按任务规模精简。先给可操作结论，再给证据和限制，不列与改动无关的通用检查清单。
