# 验证证据与复现

## 同一快照

每项运行证据注明版本与环境。指定提交不等于当前工作区；运行现有工作区测试前先确认它能证明哪个层。需要复现指定版本时读取相应Git对象，在系统临时目录构造受控副本或内存执行最小真实路径，不修改用户源码、测试、index或HEAD。使用临时副本时记录遗漏的构建、依赖和生成条件，不能将删掉的环境当作完整产品。

不要checkout用户工作区来验证旧版本；新测试或故障注入写在隔离环境，不自动添加到项目。现有测试可能产生缓存、文件、网络、费用或真实配置副作用，先读入口与项目隔离机制，再选安全运行方式；没有条件就报告未执行，不突破授权。

## 证据强度

绿色lint/typecheck/覆盖率不能证明错误路径、边界或最终效果正确。作者声称检查通过要核对确切版本、实际命令和选中范围；跳过、取消、未运行、没有用例均不是通过。

找能区分base与head或能推翻假设的证据。完整复现优先走真实公开入口；隔离的局部探针能证明局部行为，但其局限要列出。也可用清楚的同版本调用链建立确定缺陷，不要求每项都能动态运行后才允许报告。

## 检查是否有效

- 正向测试只证明对应成功场景；针对改动补核拒绝、失败、取消、边界和清理中适用情况。
- 回归测试必须针对目标保证；必要时在临时环境撤销修复或注入受控故障，确认测试因正确原因失败，编译失败和跳过不算语义负例。
- 通过新测试后仍要核对它经过真实执行入口，是否被mock、手工直调或规范化绕开实际加载/权限路径。
- 断言应观察外部状态、文件字节、事件、输出或释放，而非复述实现或只相信报告。
- 异步/资源测试要拥有端口、路径、进程和订阅；等待真实同步条件，不靠任意sleep制造或掩盖竞争。
- 性能变化使用实际测量与适用环境；代码更短、覆盖更高、包更少不等于结果更好。

安全负例只作用于隔离资源。没有可控方式时列验证缺口，不故意破坏用户环境或生产状态。

## 失败与判断边界

检查失败要定位是本次回归、已有问题、环境不满足或证据不足；不能未经复核说「main也失败」就忽略，也不能自动把所有失败归给本次改动。已有问题在需要时单列，不伪装成diff引入的缺陷。

按影响与项目规则选检查，不强制通用全量矩阵。用项目真实工具命令，用户要求jmvn时不用mvn。需要凭据、平台、服务或费用而无法执行时说明条件；公开消费者和历史数据的未知范围仍要报告。自动检查发现的问题解释其影响，不重复堆砌同一根因；绿色检查未覆盖的语义缺陷照常报告。
