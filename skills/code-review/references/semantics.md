# 按改动影响进行语义审查

先确定项目要求与所改对象，读取其契约和真实消费者，再选择下面相关方向。它们是判断线索，不是每次必须跑完的固定清单；框架专属规范由目标项目决定，不把单例、某种状态或包布局一律判错。

## 意图、调用方与执行入口

输入如何进入、由谁校验/转换、谁执行、状态和副作用怎样被读取？看修改行也追未改动调用方、动态清单、插件、公共SDK/CLI和构建产物中适用入口。UI/包装器/模式过滤可能只隐藏某条路径，直接或其他消费者仍能调用执行器。

权限拒绝、配置限制和资源上限要在真正执行义务的所有者处生效。仅在界面检查权限不证明worker入口安全。边界覆盖最终发出/保留的完整值，包含包装和元数据；按实际单位检查极小、恰好边界、超大单项和多字节情况。

## 失败、状态与恢复

检查异常分类、传播与处理责任、失败后的可信状态、是否继续依赖操作和用户报告。读取/解析失败不自动表示空值；恢复后必须重新满足后续操作前提。捕获并继续若掩盖未知结果、旧数据或未完成事务，应建立具体失败路径证明。

错误提示变化不能替代修复真实失败。预览/dry-run若按项目契约只读，追到实际写入或外部动作；表面返回preview不证明没有副作用。日志、事件和恢复标志可能承担持久事实，不能因为界面不显示就删。

## 生命周期、并发与所有权

识别资源取得、发布、取消、异常、回调重入、释放和释放完成的责任。测试开始后取消、await中失败、竞争终态与重复调用中适用路径，确认不泄漏、不重复提交、不在依赖释放后继续使用。多标志或多个控制器可能重复，也可能代表不同事实；依据真实状态判断。

共享值是借用、快照还是拥有？同id不保证对象身份，浅复制/浅冻结不保证深层隔离。缓存、通知、UI、持久化、重放和查询视图应与文档承诺的成功点一致，不能在操作失败前提前发布成功。

## 兼容、配置与平台

核对公开输入接受、序列化、持久化、版本迁移、默认值、配置优先级和动态消费者。被转发的值可能被后续默认覆盖；没有仓内固定调用不证明公共字段可删。跨平台类型/路径/进程语义应核对目标环境，交叉编译不等于实际运行通过。

新增默认值、操作集合和公共API需要实际消费者或明确产品依据。新增测试或决定只表达方案本身，不能独自证明该方案必要。已有设计理由是讨论依据，若只是另一种合理设计或维护偏好，作为建议而非缺陷。

## 文档、输出与范围

配置、错误、字段、状态、行为变化同步受影响参考、模块说明和必要注释。新文字要核对完整语义，格式检查不证明准确。提案转实施时状态、路径和现在时正文匹配实际范围；缺调用方或迁移证据不能冒称全部完成。

用户可见/模型可见输出按实际接收者核对，说明是否需要项目已有快照或端到端证据。翻译、可访问性和平台UI只有真实涉及才审；不强制其他项目的字典/框架模式。无关重构与能力变化要有范围依据，但不要把合理局部改进自动当阻断问题。
